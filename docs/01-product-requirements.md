# AI Academy — Product Requirements

## 1. Problem

Self-study of AI is dominated by passive consumption: videos watched, blog posts skimmed,
notebooks copied. None of it verifies understanding, and none of it adapts. AI Academy is a
single-student (initially) learning system that teaches AI from first principles and **refuses
to advance the student until mastery is demonstrated**.

## 2. Users

| User | Description |
|---|---|
| Student | The primary user. ~1 hour/day, 12–24 month horizon. Wants mastery, not badges. |
| Admin (same person, initially) | Can override grades, inspect AI calls/costs, re-run jobs, edit curriculum. |

Multi-tenant support is designed in (every row is user-scoped) but not a product goal for v1.

## 3. Goals and non-goals

**Goals**
1. Mastery-gated progression across a dependency graph of concepts.
2. Lessons generated incrementally from structured specs + the student's real performance.
3. Grading that is evidence-based, auditable, reproducible, and robust to LLM noise.
4. Real coding work, executed in a sandbox with public and hidden tests.
5. Automatic delivery: pass → next lesson prepared → email with a direct link.
6. Spaced retrieval of previously mastered concepts.

**Non-goals (v1)**
- Gamification (points, leaderboards, badges). A streak counter is the only concession.
- Multi-student classrooms, instructors, payments.
- GPU sandboxes (Block 7+ needs them; the sandbox interface is designed to accept a GPU backend later).
- Mobile apps (responsive web only).

## 4. Core user journeys

### J1 — Onboarding
Welcome → program overview & roadmap → background questionnaire (math, programming, ML, AI;
self-rating 0–4 each plus free text) → optional diagnostic (short objective quiz on Block 1
concepts) → daily goal (default 60 min), timezone, delivery preferences → profile created →
first eligible lesson prepared and emailed.

Diagnostic results set **prior** mastery estimates. Priors never unlock content on their own;
they make a lesson *test-out eligible* (the student may jump straight to its assessment and
pass it to skip the instruction). Mastery still requires passing the assessment.

### J2 — Daily lesson
Email ("Lesson 3 is ready: Derivatives, gradients, and the chain rule", objectives, ~60 min,
why it matters, connections, link) → lesson viewer:
retrieval warm-up → concept → math deep-dive → interactive demo → active recall →
coding/applied → summary. Each section is marked complete as the student works. Tutor,
notes, and resources are always one click away.

### J3 — Submission and grading
Student submits all required answers (one submission per attempt, idempotent). Grading runs
in the background: deterministic items instantly, free-response via rubric-based LLM grading
(with a second pass when borderline), code via sandboxed tests + static checks + AI review.
The student sees per-question feedback: score, rubric breakdown, concepts demonstrated, missing
concepts, incorrect claims, explanation, next steps, and whether the mastery bar was met.

### J4 — Failure and remediation
Fail → failed objectives identified → misconceptions diagnosed → targeted mini-lesson with a
*different* explanation → focused practice → new, distinct questions on the same objectives →
regrade. On the second failure of the same objective, the remediation reaches back to
prerequisite concepts instead of re-explaining the same thing.

### J5 — Module/project gates
After a module's lessons pass, the module assessment (≥85%) and the module's coding project
(≥90%, milestone-based, multi-day) must both pass before the next module unlocks. The student
may keep working on lessons within the module while the project is pending.

### J6 — Spaced review
Mastered concepts get review dates. When due, a short retrieval quiz (3–5 items, ~5 min) is
offered on the dashboard and optionally by email. Review results adjust the concept's
stability; a failed review moves the concept to *at risk* / *requires remediation*.

## 5. Functional requirements (MVP)

| # | Requirement | Acceptance |
|---|---|---|
| F1 | Auth | Email + password, HTTP-only session cookie, email verification link |
| F2 | Curriculum | Full 18-block outline visible on roadmap; Block 1 has concepts, prerequisites, module/lesson specs |
| F3 | Lessons | Typed `LessonContent` (Pydantic + Zod), rendered with Markdown, KaTeX, code highlighting, interactive widgets, embedded video |
| F4 | Generation | Next lesson generated by Lesson Author from spec + mastery + misconceptions + budget, validated, optionally reviewed, versioned |
| F5 | Resources | Resources carry a verification status; URLs are HTTP-checked; unverifiable ones are hidden or marked |
| F6 | Assessment | MCQ, multi-select, numeric, short/long answer, derivation, code |
| F7 | Grading | Deterministic objective grading; rubric LLM grading with evidence + confidence + second pass; manual override |
| F8 | Code | In-browser Monaco editor; sandboxed execution of public + hidden tests; static algorithm checks; AI review |
| F9 | Mastery | Objective- and concept-level estimates; critical-objective gating |
| F10 | Progression | State machine per lesson/module; idempotent; audited |
| F11 | Remediation | Plans, mini-lessons, distinct variant questions, prerequisite fallback |
| F12 | Email | Resend/SMTP behind an interface; idempotent notifications; preferences; unsubscribe; delivery hour in local timezone |
| F13 | Dashboard | Current position, progress, streak, grades, mastered/needs-review concepts, project status, next lesson, roadmap |
| F14 | Tutor | Lesson-aware chat with five modes; never reveals graded solutions |
| F15 | History | All submissions, grades, feedback, notes, tutor chats preserved |
| F16 | Cost | Every AI call logged with tokens and cost; monthly budget enforced |

## 6. MVP content slice

| # | Lesson | Module |
|---|---|---|
| 1 | Vectors, dot products, and geometric intuition | 1.1 Vectors & Matrices |
| 2 | Matrix multiplication and linear transformations | 1.1 Vectors & Matrices |
| 3 | Derivatives, gradients, and the chain rule | 1.2 Calculus for Learning |
| 4 | Gradient descent and optimization | 1.3 Optimization Foundations |
| 5 | Implementing gradient descent from scratch | 1.3 Optimization Foundations |
| — | Foundations Checkpoint (cumulative, ≥85%) | 1.3 |
| — | Project: Linear regression by gradient descent (3 milestones, ≥90%) | 1.3 gate |

Lessons 1–5 ship as hand-authored seed content (they double as quality exemplars for the
generator and as fixtures for tests). All later lessons in the curriculum are generated on
demand when they become eligible.

## 7. Success criteria for the MVP

The end-to-end test `test_full_learning_lifecycle` must demonstrate: complete lesson → submit →
graded with meaningful feedback → fail → remediation generated → pass the variant assessment →
next lesson published → email sent exactly once.

## 8. Assumptions (documented, revisit as needed)

1. **One student, self-hosted.** Designed multi-user, operated single-user.
2. **Postgres is the queue.** A `background_jobs` table with `SELECT … FOR UPDATE SKIP LOCKED`
   replaces Redis + a worker framework. One fewer service; jobs are transactional with the state
   they mutate. Swap for a dedicated queue if throughput ever matters (it won't for one student).
3. **Default delivery is immediate.** Passing a lesson emails the next one right away; the
   student may configure a daily delivery hour instead.
4. **Seed lessons are hand-authored**, later lessons AI-generated. This makes the platform usable
   and testable without an API key and gives the generator concrete exemplars.
5. **Videos are linked/embedded, never downloaded.** Book references are metadata only.
6. **Thresholds are configurable** (see `backend/app/config.py` → `ProgressionThresholds`).
7. **Test-out is allowed** but requires passing the real assessment.
8. **The original spec text was truncated at "Phase 6: Automation"**; phases 6+ are inferred
   (automation/email scheduling, then hardening and deployment).
